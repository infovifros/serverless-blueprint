# serverless-blueprint — Claude Code Guide

This file is read automatically by Claude Code at session start.
Follow these conventions precisely when adding or modifying code in this project.

## Project overview

`serverless-blueprint` is a production-ready AWS Serverless starter built on
[`@vifros/aws-serverless-core`](https://github.com/infovifros/aws-serverless-core).

It ships with a fully-functional in-memory CRUD API (entity: **Item**) that
demonstrates the recommended patterns for the wider platform.  When starting a
real service, replace the in-memory store with your database of choice.

**Stack:**
- Runtime: Node.js 22, TypeScript 5
- Framework: Serverless Framework v3 + `serverless-offline`
- Handler base classes: `@vifros/aws-serverless-core` (`APIHandler`, `HandlerResponse`, `HandlerError`, `Logger`)
- Validation: AJV via JSON Schema (auto-generated by `scripts/schema-generator.sh`)
- Documentation: OpenAPI 3.0 (auto-generated by `scripts/generate-swagger.js`)

## Handler pattern — the golden rule

Every HTTP endpoint follows this exact three-file structure:

### 1. `handler.ts` — Lambda entry point (thin)
```typescript
import {APIHandler, HandlerResponse} from '@vifros/aws-serverless-core';
import {StatusCodes} from 'http-status-codes';
import {MyRequest} from './interfaces/my-action.interface';
import mySchema from './schema/schemaValidator.json'; // only if body validation needed
import myAction from './my-action';

async function initHandler(request: MyRequest): Promise<HandlerResponse> {
  const response = await myAction(request);
  return new HandlerResponse(response, StatusCodes.OK);
}

export const handler = new APIHandler(initHandler, {
  schemaValidator: mySchema, // omit if no body validation
}).lambdaHandler;
```

### 2. `my-action.ts` — Business logic
```typescript
import {HandlerError, Logger} from '@vifros/aws-serverless-core';
import {StatusCodes} from 'http-status-codes';
import {MyRequest} from './interfaces/my-action.interface';

const logger = new Logger();

async function myAction(request: MyRequest): Promise<ResponseType> {
  logger.info('[myAction] Processing request', {relevantField: request.someField});
  // ... logic here
  return result;
}

export default myAction;
```

### 3. `interfaces/my-action.interface.ts` — Request shape
```typescript
import {Request} from '../../../../common/interfaces/request.interface';

export interface MyActionRequest extends Request {
  /**
   * @TJS-description ##path## UUID of the resource.  ← path param
   * @TJS-description ##query## Filter by status.     ← query string
   * @TJS-description ##body## Display name.          ← request body field
   */
  id: string;
}
```

## Key classes from `@vifros/aws-serverless-core`

### `APIHandler`
Wraps your handler function and provides:
- Automatic request parsing (body + path params + query string merged into one object)
- JSON Schema validation via AJV (pass `schemaValidator` option)
- Structured error handling and SNS alerts
- gzip compression when `Accept-Encoding: gzip` is present

```typescript
export const handler = new APIHandler(initHandler, {
  schemaValidator: mySchema,         // optional
  resourcesToLoad: [Resources.LOGGER], // optional shared resources
}).lambdaHandler;
```

### `HandlerResponse`
Return this from every handler function.  `null` body → HTTP 204.
```typescript
return new HandlerResponse(data, StatusCodes.CREATED);
return new HandlerResponse(null, StatusCodes.NO_CONTENT); // 204
```

### `HandlerError`
Throw this for expected failures.  `alertFlag = false` suppresses SNS alerts.
```typescript
throw new HandlerError('Item not found', StatusCodes.NOT_FOUND, false, false);
//                      message            statusCode              stack alert
```

### `Logger`
Always use this — never use `console.*` directly.
```typescript
const logger = new Logger();
logger.info('[myAction] Message', {key: 'value'});
logger.error('[myAction] Something failed', error);
```
Log prefix convention: `[ClassName.methodName]`

## Naming conventions

| Thing | Convention | Example |
|-------|------------|---------|
| Handler folder | `kebab-case` | `create-item/` |
| Handler function name | `camelCase` | `createItem` |
| Interface name | `PascalCase + Request` | `CreateItemRequest` |
| Serverless function key | `kebab-case` | `create-item` |
| API path | `/v1/resource` | `/v1/items` |
| Log prefix | `[FileName.methodName]` | `[createItem] Creating` |
| Error enum key | `PascalCase` | `ItemNotFound` |

## Adding a new HTTP endpoint

Use the Claude Code slash command:

```

```

Then describe what you need in plain English, e.g.:

> I want a POST endpoint at `/v1/orders` called `create-order` that accepts `productId` (string, required), `quantity` (integer ≥ 1, required), and `notes` (string, optional).

## Environment variables

All env vars are defined per stage in `config/env/`:
- `local.yml` — local development (serverless-offline)
- `dev.yml` — AWS dev deployment

Add new variables to **both** files.  AWS SSM / Secrets Manager is the recommended
approach for real secrets — never commit actual secret values.

---

## Code style rules

- **No `any` types** — use proper TypeScript types or `unknown`
- **No `console.*`** — always use `Logger`
- **All comments and variable names in English**
- **Descriptive variable names** — prefer `createdItem` over `item`, `itemId` over `id`
- Prettier + ESLint enforce formatting automatically

## Postman

Import both files from the `postman/` folder:
1. `serverless-blueprint.collection.json` — the request collection
2. `serverless-blueprint.environment.json` — the environment (sets `baseUrl = http://localhost:4000`)

Run requests in order: **List → Create → Get → Update → Delete**.
The Create request automatically stores the returned `id` in the `itemId` environment variable.
